## FAQ（よくある質問）

### Q1: なぜ既存のギフトアプリではダメなのか？

**A1**: 既存のギフトアプリは「相手を喜ばせたい善意」に依存しており、ユーザーに「選択」と「判断」を強いるからです。

**既存アプリの問題点**：

1. **動機の不一致**：「相手を喜ばせたい」という善意を前提とするが、実際のユーザーは「自分の評価を維持したい」という保身が動機
2. **選択肢の提示**：複数のギフト候補を提示し、ユーザーに選ばせる → 思考コストが高い
3. **構造化データへの依存**：誕生日などの構造化データを手動入力させる → 入力摩擦が高い
4. **タイミングの判断**：いつ贈るかをユーザーに判断させる → 社会的マナーの知識が必要

**コミュ♥外chuの解決策**：

1. **動機の転換**：「保身・防衛」を動機とし、「これ買っとけばさらに安泰っす👍」という処方箋として提示
2. **唯一の正解を提示**：ADが「唯一の正解（台本）」を提示し、ユーザーは思考停止でポチるだけ
3. **非構造化データからの抽出**：LINEスクショ、音声メモ、Gmail、Google Photosなどから自動抽出 → 入力摩擦ゼロ
4. **タイミングの完全自動化**：社会的マナーに基づく「時差」通知ロジックで、完璧なタイミングを自動計算

**コンバージョンの必然性**：  
ユーザーは「思考停止でポチる」だけで、社会的に生き残るための防衛が完了する。極めて高いCVR（購買率）を実現する。

### Q3: 返報性ハックのタイミング計算は、なぜそこまで複雑なのか？

**A3**: 社会的マナーには「時差」があり、「早すぎて事務的」にも「遅すぎて失礼」にもならない完璧なタイミングを自動計算する必要があるからです。

**二段階返報ロジックの設計思想**：

**第一段階：即効性お礼カンペ通知（24時間以内）**

- **目的**：「気が利かない人」認定される前に、秒でお礼を伝えて「マメな人」として評価される
- **タイミング**：事象発生から24時間以内
- **重要な教育**：ADがユーザーに「即時ギフト返しは早すぎて事務的（突き返しているよう）で失礼」であることを説明

**ADのセリフ例**：
```
お疲れーっす！昨日の件、とりあえず今日はお礼のLINEだけ送っときましょ！
お返しは今すぐだとガッツいてる感（事務的）出ちゃうんで、時期が来たらまたリマインドしますね👍

『この前のお酒、めっちゃ美味しかったです！ありがとうございました』
```

**第二段階：遅効性ギフト提案通知（2〜3週間後）**

- **目的**：「早すぎて事務的」にも「遅すぎて失礼」にもならない完璧なタイミングを自動計算
- **タイミング**：事象発生から21日後（MVP）、次回予定の3日前（決勝用）

**段階的拡張アプローチ**：

| フェーズ | タイミング計算ロジック | 実装方式 |
|---|---|---|
| **MVP段階** | 固定スケジュール（21日後） | EventBridge Schedulerのみ |
| **決勝用** | 動的再計算（次回予定の3日前） | カレンダーWebhook統合 |

**エッジケース処理（決勝用）**：

| ケース | 処理方法 | 理由 |
|---|---|---|
| 次回予定が2週間以内 | デフォルトを維持 | 「早すぎて事務的」を避ける |
| 次回予定が2〜3週間後より早い | 次回予定直前（3日前）に変更 | 「会う時に渡す」タイミング |
| 次回予定が2〜3週間後より遅い | デフォルトを維持 | 「遅すぎて失礼」を避ける |
| 次回予定がキャンセル | デフォルトにフォールバック | 安全な選択 |

**マナーの時差（遅延評価）**：  
システムがすべてのタイミング判断を行い、ユーザーは一切の判断を放棄できる。

### Q4: モックデータ戦略とは何か？なぜ高速開発が可能なのか？

**A4**: フロントエンド開発をバックエンドAPIの完成を待たずに先行実装する「モックデータ戦略」を採用しているからです。

**モックデータ戦略の利点**：

1. **並行開発の実現**：Unit-UI（フロントエンド）とUnit-AD（AI統合）を先行実装し、Unit-DB（データベース）とUnit-Integration（API）を後から実装
2. **開発スピードの向上**：フロントエンド開発がバックエンドにブロックされない
3. **UI/UX検証の早期化**：バックエンドAPIの完成を待たずに、UI・画面遷移を先行して完成させる

**実装方式**：

```typescript
// MockDataProvider.tsx
const mockEpisodes = [
  {
    episode_id: "ep-12345",
    target_name: "叔父さん",
    episode_content: "腰痛いらしい",
    emotion_tag: "🤒 体調悪そう",
    created_at: "2026-05-08T18:00:00Z"
  }
];

export const MockDataProvider = ({ children }) => {
  return (
    <DataContext.Provider value={{ episodes: mockEpisodes }}>
      {children}
    </DataContext.Provider>
  );
};
```

**切り替え戦略**：
- MVP段階：モックデータでUI/UX検証
- 決勝用：リアルAPIに切り替え（環境変数で制御）

この戦略により、ハッカソンのスピードを維持し、フロントエンド開発がバックエンドにブロックされない並行開発を実現しました。

### Q5: なぜAmazon PA-APIを使わず、商品詳細ページ方式を採用したのか？

**A5**: 保守性の向上と実装の簡素化を両立するためです。

**理由**：

1. **保守性の向上**：Amazon Remote Cart URLはセキュリティ仕様変更に弱いため、全フェーズ（MVP・決勝）で商品詳細ページ方式を採用
2. **実装の簡素化**：PA-APIの認証・リクエスト処理が不要
3. **UX設計の委譲**：ユーザーの「摩擦ゼロ体験」は、Amazon側の『今すぐ買う（1-Click）』機能に委ねる

**実装方式**：

```
1. Bedrockが推奨商品のASINを選択
2. ASIN指定の商品詳細ページURL（アソシエイトリンク）を生成
   例: https://www.amazon.co.jp/dp/B0XXXXXX?tag=associate-id
3. ユーザーが「よきに」ボタンをタップすると、商品詳細ページに遷移
4. Amazon側の『今すぐ買う（1-Click）』機能で購入完了
```

**UX設計**：
- 1-Click設定済みユーザー：商品詳細ページで1タップで購入完了
- 未設定ユーザー：「カートに入れる」ボタンが目立つ位置に配置されている

**重要な設計思想**：  
この「よきに」UXは本システムの核心的な思考停止体験を実現する必須機能です。
