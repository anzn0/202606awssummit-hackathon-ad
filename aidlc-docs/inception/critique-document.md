### ✅ 改善2: パフォーマンス要件の定量化

**追加内容**:

#### MVPスコープ（P0）: 最低限のパフォーマンスライン
| 機能 | 目標（P95） | 許容最大値 |
|---|---|---|
| カンペ生成 | 10秒以内 | 15秒 |
| スクショ解析 | 15秒以内 | 20秒 |
| CRUD API | 2秒以内 | 3秒 |
| プッシュ通知 | 2分以内 | 5分 |

#### 決勝用フルスコープ（P2）: 現実的なパフォーマンス目標
| 機能 | 目標（P95） | 許容最大値 | 最適化手法 |
|---|---|---|---|
| カンペ生成 | 5秒以内 | 8秒 | プロンプト最適化、キャッシング |
| スクショ解析 | 10秒以内 | 15秒 | 画像圧縮、並列処理 |
| CRUD API | 500ms以内 | 1秒 | GSI最適化 |
| プッシュ通知 | 30秒以内 | 1分 | EventBridge最適化 |

**効果**:
- 主観的な「待たされている感」を定量的な目標値に変換
- MVP段階では機能検証を優先（パフォーマンスは最低限）
- 決勝用では現実的な範囲で最適化

---

### ✅ 改善3: 返報性ハックタイミング計算の簡略化

**追加内容**:

#### MVPスコープ（P0）: 固定スケジュール方式
- タイミング: 事象発生から**21日後（固定）**
- カレンダー連携なし
- シンプルな実装（EventBridge Schedulerのみ）

#### 決勝用フルスコープ（P2）: 動的再計算方式
- デフォルト: 21日後
- 次回予定優先: 21日以内に予定がある場合は予定の3日前
- エッジケース処理: 複数予定、予定キャンセル等

**効果**:
- MVP実装の複雑性を大幅に削減
- 決勝用で高度化する明確なロードマップ
- テストが容易（固定日数）

## 3.2 実行した改善

### ✅ 改善6: エラーハンドリング実装パターンの追加

**追加内容**:

1. **リトライロジック（防御的操作）**
   - Bedrock呼び出し: 最大3回リトライ、adaptive mode
   - DynamoDB操作: 最大3回リトライ、指数バックオフ

2. **サーキットブレーカー（Bedrock障害対策）**
   - 閾値: 5回失敗でOPEN
   - タイムアウト: 60秒
   - リセットタイムアウト: 30秒

3. **フォールバック（楽観的操作）**
   - Bedrock障害時: デフォルトカンペ表示
   - ギフト提案失敗時: ギフト提案をスキップ

4. **構造化ログ**
   - AWS Lambda Powertools使用
   - JSON形式、CloudWatch Logs

5. **エラー分類とハンドリング戦略**
   - 認証エラー: 即座に401、リトライなし
   - Bedrock障害: リトライ3回 → フォールバック
   - DynamoDB障害: リトライ3回（指数バックオフ）

6. **DLQ（Dead Letter Queue）設計**
   - SQS DLQ、14日間保持
   - 最大2回リトライ

7. **タイムアウト設定**
   - API Gateway: 29秒
   - Lambda（カンペ生成）: 15秒（MVP）/ 10秒（決勝用）
   - Bedrock呼び出し: 10秒（MVP）/ 8秒（決勝用）

8. **エラーメトリクスとアラート（決勝用）**
   - CloudWatch Metricsへのカスタムメトリクス送信
   - CloudWatch Alarms設定

**効果**:
- エラーハンドリングの実装方法が具体化
- MVP/決勝用で段階的に実装
- 障害時の挙動が明確

---

### ✅ 改善7: フロントエンド状態管理戦略の追加

**追加内容**:

1. **グローバル状態管理（Zustand）**
   - 管理対象: ユーザー情報、認証トークン、通知設定
   - localStorage永続化

2. **サーバー状態管理（TanStack Query）**
   - 管理対象: API呼び出し、キャッシング、リトライ
   - キャッシュ時間: カンペ5分、エピソード10分、ユーザー情報1時間

3. **ローカル状態管理（React Hooks）**
   - 管理対象: フォーム入力、UI状態（モーダル開閉等）

4. **キャッシング戦略**
   - データ種別ごとのキャッシュ時間と無効化タイミング

5. **楽観的UI更新**
   - スワイプフィードバック等で即座にUI更新
   - エラー時にロールバック

6. **オフライン対応（将来拡張）**
   - PWA + IndexedDB

**効果**:
- フロントエンドの状態管理方針が明確化
- MVP: React useStateのみ、決勝用: Zustand + TanStack Query
- パフォーマンスとUXの向上

### 決勝用開発時の推奨事項
1. **品質・パフォーマンス強化**: 非機能要件ストーリー（Epic 9）を実装

4. **自動テスト**: 統合テスト、E2Eテスト、CI/CD統合

### 将来拡張時の推奨事項
1. **トレーサビリティマトリクス**: 要件IDとストーリーIDの紐付け
2. **セキュリティ強化**: フィールドレベル暗号化、CSRF対策、XSS対策
3. **オフライン対応**: PWA + IndexedDB

#### MVPスコープ（P0）: 固定スケジュール方式
- タイミング: 事象発生から**21日後（固定）**
- カレンダー連携なし
- シンプルな実装（EventBridge Schedulerのみ）

**実装方式**:
```
1. エピソード記録時: 「もらった」フラグをDynamoDBに保存
2. EventBridge Scheduler: 21日後の通知をスケジュール登録
3. 21日後: Lambda関数が通知を送信
```

**メリット**:
- 実装が単純（EventBridge Schedulerのみ）
- テストが容易（固定日数）
- MVP開発スピード重視

#### 決勝用フルスコープ（P2）: 動的再計算方式
- デフォルト: 21日後
- 次回予定優先: 21日以内に予定がある場合は予定の3日前
- エッジケース処理: 複数予定、予定キャンセル等

**実装方式**:
```
1. エピソード記録時: デフォルトスケジュール（21日後）を登録
2. カレンダーWebhook: 新規予定追加時にタイミング再計算
3. タイミング再計算: 次回予定が21日以内なら予定の3日前に変更
4. EventBridge Scheduler更新: スケジュールを動的に更新
```
