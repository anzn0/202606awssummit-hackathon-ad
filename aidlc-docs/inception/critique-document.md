### 1.2 現実的なスコープ管理 ✅

**評価**: 優秀

### 2.2 ✅ 返報性ハックの実装複雑性 - **完全解決**

**初版評価（2026-05-09）**: 🔴 重大なリスク

**更新版評価（2026-05-10）**: 🟢 **完全対策済み**

「二段階返報ロジック（マナーの時差）」は、プロダクトの核心的な価値提案であり、初版レビュー時は実装の複雑性が過小評価されていた。

#### 問題点（初版 - 返報性ハック）

1. **タイミング計算の複雑性**
   - 要件: 「24時間以内」「2〜3週間後」「次回予定直前」の3つのタイミング
   - 現実: 「次回予定直前」は予定が動的に変更される可能性があり、リアルタイム再計算が必要
   - リスク: EventBridge Schedulerの動的更新が複雑

2. **エッジケースの未定義**
   - 未定義: 「次回予定がない場合」「予定が直前にキャンセルされた場合」「2〜3週間後と次回予定直前が重複する場合」
   - リスク: 実装中に仕様の曖昧さが露呈

3. **通知の重複・欠落リスク**
   - 要件: 第一段階（24時間以内）と第二段階（2〜3週間後）の2段階通知
   - リスク: EventBridge Schedulerの障害時に通知が欠落、または重複送信

#### 解決状況（2026-05-10）

✅ **タイミング計算ロジックの詳細設計完了** (`henpou-timing-logic.md`)
- 状態遷移図の定義（MVP段階と決勝用フルスコープの2段階）
- 第一段階（24時間以内）の計算式とエッジケース対応
- 第二段階（デフォルトスケジュール: 2〜3週間後）の計算式
- 動的再計算ロジック（決勝用フルスコープ）の設計

✅ **エッジケースの完全定義**
| エッジケース | 対応 |
|---|---|
| 深夜にエピソード作成 | 翌朝9時に調整 |
| 次回予定が2週間以内 | デフォルトを維持（「早すぎて事務的」を避ける） |
| 次回予定がキャンセル | デフォルトにフォールバック |
| Webhook障害 | デフォルトで通知される（安全な設計） |

✅ **EventBridge Scheduler設計の完成**
- スケジュール登録・削除の実装例
- 冪等性キーによる重複送信防止
- DynamoDBスキーマの定義

✅ **段階的拡張アプローチの明確化**
- **MVP段階**: デフォルトスケジュールのみ（外部API依存なし、シンプル・高速・安定）
- **決勝用フルスコープ**: カレンダーWebhook統合による動的再計算

#### 評価
**🟢 ブロッカー解消**: 返報性ハックの実装複雑性は完全に解決され、MVP段階では外部API依存を排除したシンプルで安定した実装が可能。

#### 解決状況（2026-05-10）

✅ **API契約仕様書の完成** (`api-contract-specification.md`)
- RESTful Resources（11 endpoints）: User、Target、Episode、Feedbackの完全なRequest/Responseスキーマ
- RPC-style Actions（3 endpoints）: SubmitTaredaka、GenerateKanpe、ScheduleHenpouの完全なRequest/Responseスキーマ
- AI Integration（5 endpoints - 内部API）: 知識抽出、カンペ生成、NG話題検出、商品ASIN選択の完全なRequest/Responseスキーマ
- Notification（1 endpoint - 内部API）: プッシュ通知送信の完全なRequest/Responseスキーマ

✅ **統一されたエラーレスポンス構造の定義**
```json
{
  "error": {
    "code": "ERROR_CODE",
    "message": "Human-readable error message",
    "details": {
      "field": "Additional error details (optional)"
    }
  }
}
```

✅ **エラーコード一覧の定義**
- 400: `INVALID_REQUEST`（リクエストパラメータが不正）
- 401: `UNAUTHORIZED`（認証トークンが無効または期限切れ）
- 403: `FORBIDDEN`（アクセス権限がない）
- 404: `NOT_FOUND`（リソースが見つからない）
- 409: `CONFLICT`（リソースの競合）
- 500: `INTERNAL_SERVER_ERROR`（サーバー内部エラー）
