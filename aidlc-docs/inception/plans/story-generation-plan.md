# User Stories Generation Plan - コミュ♥外chu

## Planning Context
このプランは、コミュ♥外chu（ゆるふわカンペAD）のユーザーストーリーを生成するための詳細な実行計画です。

---

## Story Generation Questions

以下の質問に回答してください。各質問の `[Answer]:` タグの後に回答の記号（A, B, C...）を記入してください。

### Question 1: ペルソナの詳細度
ペルソナをどの程度詳細に定義しますか？

A) 簡易版（名前、役割、主要な動機のみ）
B) 標準版（名前、役割、動機、ゴール、フラストレーション、技術スキル）
C) 詳細版（標準版 + 背景ストーリー、1日の流れ、使用デバイス、引用コメント）
X) Other (please describe after [Answer]: tag below)

[Answer]: B.「面倒くささの極致」を表現するコンセプトが大事なので、AIに「ユーザーのゴール（評価維持）」と「フラストレーション（脳のメモリを使いたくない）」の2点だけは絶対にブレずに認識（標準版としてインプット）させておきたい。

### Question 2: ストーリーの粒度
ユーザーストーリーの粒度（サイズ）はどうしますか？

A) 大粒度（Scene単位で1ストーリー：Scene 1 = 1ストーリー）
B) 中粒度（Scene内の主要機能ごとに分割：Scene 1 = 2〜3ストーリー）
C) 小粒度（ユーザーアクション単位で細分化：Scene 1 = 5〜7ストーリー）
X) Other (please describe after [Answer]: tag below)

[Answer]: X) Other: チームの役割分担（UI、DB/API、プロンプト）に合わせ、技術レイヤー（Frontend/Backend/AI Integration）で中粒度に分割する。「Scene 1の体験」という共通のコンテキスト（親エピック）を持たせつつ、Kiroにはレイヤーごとの実装を独立して行わせる。

### Question 3: ストーリーの整理方法
ストーリーをどのように整理しますか？

A) ユーザージャーニー順（Scene 1 → Scene 2 → Scene 3 → Scene 4）
B) 優先度順（MVP必須機能 → MVP拡張機能 → 決勝用機能）
C) Epic階層構造（Epic: 撮れ高報告 > Story: ワンタップ入力、音声メモ、画像アップロード）
D) ペルソナ別（ターゲットユーザー視点 → 関係者視点 → AD視点）
X) Other (please describe after [Answer]: tag below)

[Answer]: B.「まずはダミー予定からADを呼び出して、カンペとAmazonリンクを出す（体験のコア）」というMVPを確実に予選までに作り上げ、余った時間や本選（決勝）に向けて「スクショ解析」や「Googleフォト連携」といった複雑な機能（拡張機能）をAIに実装させる、という鉄壁のスケジュール管理が可能になる。

### Question 4: 受容基準の詳細度
各ストーリーの受容基準（Acceptance Criteria）をどの程度詳細に記述しますか？

A) 簡易版（Given-When-Then形式で1〜2個）
B) 標準版（Given-When-Then形式で3〜5個 + エッジケース）
C) 詳細版（標準版 + UI要件、パフォーマンス要件、セキュリティ要件）
X) Other (please describe after [Answer]: tag below)

[Answer]: A.システムとしての堅牢性よりも「ADの口調」や「手書き風のUI」といった定性的な体験（エモさ）が命なので、
受容基準をガチガチに固めてAIを縛り付けるよりも、【A】を選択して「大枠のロジック」だけをAIに爆速で作らせ、細かいUIやプロンプトの調整は人間（デザイナーや企画担当）が手を入れる、という役割分担にしたい。

### Question 5: MVP vs 決勝用の扱い
MVP（Scene 1〜4）と決勝用（Scene 0, 5, 6）のストーリーをどう扱いますか？

A) MVPのみ作成（Scene 1〜4のみ）
B) MVP優先、決勝用は簡易版（MVPは詳細、決勝用は概要のみ）
C) すべて同じ詳細度で作成（Scene 0〜6すべて）
X) Other (please describe after [Answer]: tag below)

[Answer]: B.Scene0をストーリーに含めていないので、AIに「未来の拡張性（DBスキーマの柔軟性など）」だけを担保させつつ、全力でMVPの「体験」を作らせたい

### Question 6: AD人格のストーリー化
「ゆるふわカンペAD」の人格をストーリーにどう反映しますか？

A) ペルソナとして定義し、各ストーリーの受容基準に「ADの語尾は『〜っすね』」等を含める
B) 別途「AD人格仕様書」を作成し、ストーリーからは参照のみ
C) ストーリーには含めず、プロンプトエンジニアリングのタスクとして扱う
X) Other (please describe after [Answer]: tag below)

[Answer]: X) Other: フロントエンドの固定テキストおよびBedrockのシステムプロンプトの調整は「Unit-AD（プロンプトエンジニアリング専任）」の独立したタスクとして切り出す。コーディング用エージェント（Kiro）には人格を意識させず、APIの繋ぎ込みとプレーンなUI構築（表示器の作成）のみに集中させる。

### Question 7: 非機能要件のストーリー化
セキュリティ、パフォーマンス、スケーラビリティなどの非機能要件をストーリーにどう含めますか？

A) 各ストーリーの受容基準に含める（例: 「カンペ生成は5秒以内」）
B) 別途「非機能要件ストーリー」として独立させる
C) ストーリーには含めず、NFR Requirements（後続フェーズ）で扱う
X) Other (please describe after [Answer]: tag below)

[Answer]: X) Other: 予選向けMVPの段階では、パフォーマンス・スケーラビリティなどの非機能要件は「完全にスコープ外（無視）」とする。AIコーディングエージェントはNFRを一切考慮せず、機能の実現とUXの構築（体験のWow!）にのみ全リソースを集中させること。
