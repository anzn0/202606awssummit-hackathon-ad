# 要件定義書 - コミュ♥外chu (ゆるふわカンペAD)

## プロジェクト概要

### プロダクト名
**コミュ♥外chu** (UI上の人格: ゆるふわカンペAD)  
サブタイトル: ～人間、おやすみしませんか？

### コア・アイデンティティ
Larry Wallの「怠慢 (Laziness)」の社会実装。人間関係のメンテナンス（記憶・気遣い・行動）をすべてAIに丸投げし、表は「聖人」裏は「廃人」、中身ゼロの「聖人君子」を量産する社会システム。

### プロダクトの本質（重要）
**本システムは「ギフトを贈るためのアプリ」ではありません。**

本システムは「**会話のカンペによって人間関係の事故（地雷）を防ぐ、ソーシャル・サバイバルツール**」です。

- **メイン機能**: アイスブレイクの一言カンペ、NG話題（地雷）回避アラート
- **オプション機能**: Amazonギフト提案（マネタイズのための「ついで」要素）

## 1. ビジネス要件

### 1.1 ビジネス意図と価値提案

#### 動機の転換
既存のギフトアプリが「相手を喜ばせる善意」に依存するのに対し、本サービスは「自分の評価を維持し、社会的に生き残るための保身・防衛」を動機とする。

#### コンバージョンの必然性
「Amazon ECサイトへの誘導」をメインに押し出すのではなく、ADからの「これ買っとけばさらに安泰っす👍」という「保身のための処方箋」としてECリンクを提示する。ユーザーは思考停止でポチるため、極めて高いCVR（購買率）を実現するビジネスモデル。

#### 摩擦ゼロのデータ収集
誕生日などの構造化データではなく、スクショや雑談ボイスメモ、過去の写真、メールなどの「非構造化データ」から、人間関係の文脈と「貸し借り」を抽出する。

#### 本質的価値
モノを贈る体験やTODO管理ではなく、人間関係の「事故」を防ぎ、生きやすくするライフライン。

### 1.2 ターゲットペルソナ
良好な人間関係は維持したいが、それに脳のメモリや時間を割くのが死ぬほど面倒くさい、極度の面倒くさがり（ICTサラリーマンなど）。

### 1.3 成功指標（検証条件）

#### MVP（予選）の成功指標

**【ビジネス・UX軸】**
- コア機能（Scene 1〜5）が検証可能なレベルで実装され、開発チームまたは少数のテスターの手によって「AIに丸投げできる思考停止のUX」が技術的に成立していることが確認できること
- テストユーザーが「自分で考えるよりADに任せた方が楽」と感じ、提案を受け入れる（思考停止の立証）

**【システム・技術軸】**
- デモ環境にて、Scene 1〜5（撮れ高報告、会話サバイバルカンペ、パフォーマンス、返報性ハック、PTA集会カンペ）のUIとAI連携が稼働する
- LLMの推論や解析において、ユーザーの「待たされている感（UXの阻害）」を最小限に抑える、自然なテンポで稼働すること

#### 決勝用フルスコープの成功指標

**【ビジネス・UX軸】**
- ユーザーが内容を確認せずとも「任せておけば事故らない」という絶対的な信頼（完全な思考停止）が成立する
- **実ユーザーによる受容率の検証（定量的・定性的エビデンス）**: 開発チーム以外のユーザー（友人・同僚等）にシステムを継続試用してもらい、提案されたカンペやギフトに対する「スワイプ反応（受容率）」や定性的なコメントを収集すること
- **社会的評価の向上と事故防止のヒアリング検証**: 利用ユーザーに対し、「周囲からの評価が上がった（気が利く人だと思われた）か？」「人間関係の事故（地雷）を防げたと感じたか？」というヒアリングを実施し、高い肯定的な回答率（社会的サバイバルの成功）を得ること

**【システム・技術軸】**
- AWS上でマルチモーダル解析（LINEスクショ、音声入力、Gmail、Google Photos）からスケジュール通知まで、一連のアーキテクチャが人手介入なしで完全自律稼働する
- 外部連携は「Googleアカウント連携（カレンダー、Gmail、Google Photos）」と「Amazon連携（商品ページ遷移）」に限定し、これらが自律稼働すること

### 2.1 MVPスコープ（優先度: P0 - 必須）

#### MVP定義
主要ユースケース（Scene 1〜5）の機能を実装し、データ永続化も行う。このMVPを先に完成させ、その後決勝用フルスコープへ段階的に拡張する。

#### Scene 1: 脳死での「撮れ高報告」（インプット）

##### 機能概要
予定終了後、ADから「お疲れーっす！今日の撮れ高ポチッとしといてくださーい」と通知。

##### 入力方式
1. **ワンタップ感情タグ（P0）**
   - 絵文字ボタン（🤒 体調悪そう、😊 元気そう、😰 悩んでそう等）をワンタップで記録
   - 文字入力なしで相手の状態を記録

2. **音声メモ入力（P1）**
   - 短い音声メモ（「腰痛いらしい」等）を録音
   - Amazon Nova（Bedrock）でテキスト化

3. **画像アップロード（スクショ解析）（P1）**
   - LINEスクショ等をアップロード
   - Amazon Nova（Bedrockマルチモーダル）で解析し、ナレッジ抽出

##### データ保存（P0）
- DynamoDBに人物プロファイル、エピソード、タグを保存
- API Gateway + Lambda経由でCRUD処理

#### Scene 2: 会話サバイバル・カンペの提示

##### 機能概要
次回の予定直前、ADから「とりあえずこれ読んどいてくださーい」とカンペが届く。

##### 2.1 アイスブレイクと気遣いの一言カンペ（P0）
- **目的**: 相手の直近の状況から「完璧な第一声」を生成
- **AI処理**: Amazon Nova（Bedrock）で過去のエピソードから文脈に沿ったカンペを生成
- **例**: 「『腰の調子、どうっすか？』って聞いとけばOKっす」
- **効果**: 相手に「自分のことを覚えてくれている」と錯覚させる

##### 2.2 NG話題（地雷）回避アラート（P0）
- **目的**: 絶対に振ってはいけない話題を赤字で警告
- **例**: 「⚠️ 絶対に聞いちゃダメ：『奥さん元気？』『犬は？』」
- **対象**: 離婚、ペットの死、家族の病気等
- **効果**: 社会的な死（地雷を踏むこと）を防ぐ

##### 2.3 ついでギフトの提案（P1 - オプション機能）
- **目的**: カンペの下部に「おまけ」としてAmazonギフト提案
- **表示**: 「ついでにこれ買っとけばさらに安泰っす👍」とAmazonリンク付き
- **実装方式**: Amazon PA-APIは利用せず、Bedrockが推奨商品のASINを選択し、ASIN指定の商品詳細ページ（アソシエイトリンク）への遷移で統一
  - 例: `https://www.amazon.co.jp/dp/B0XXXXXX?tag=associate-id`
- **UX設計**: ユーザーの「摩擦ゼロ体験」は、Amazon側の『今すぐ買う（1-Click）』機能に委ねる
- **重要**: これはマネタイズのための「ついで（オプション）」要素であり、メイン機能ではない

##### 2.4 スワイプフィードバック（興味あり/なし）（P0）
- **機能**: カンペやギフト提案に対してTinder風スワイプで反応
- **実装**: react-spring等のライブラリでスワイプジェスチャー実装
- **データ保存**: フィードバックをDynamoDBに保存し、次回のAD提案精度を向上

#### Scene 3: パフォーマンス

##### 3.1 カンペ表示画面（手書き風UI）（P0）
- **UI**: 手書き風フォント・スケッチブック風デザイン
- **目的**: 「圧ゼロ」の心地よい体験
- **実装**: CSSアニメーションで手書き風デザイン

##### 3.2 思考停止の「よきに」決済（P0）
- **機能**: 「よきに」ボタンをワンタップするだけで、Amazon商品詳細ページに遷移
- **目的**: 商品を探す手間を完全に省き、ADが選んだ商品に直接アクセスさせる
- **実装方式**: ASIN指定の商品詳細ページ（アソシエイトリンク）への遷移
  - Bedrockが推奨商品のASINを選択し、商品詳細ページURLを生成
  - 例: `https://www.amazon.co.jp/dp/B0XXXXXX?tag=associate-id`
  - Amazon PA-APIは利用しない
- **UX設計**: ユーザーの「摩擦ゼロ体験」は、Amazon側の『今すぐ買う（1-Click）』機能に委ねる
  - 1-Click設定済みユーザーは商品詳細ページで1タップで購入完了
  - 未設定ユーザーも「カートに入れる」ボタンが目立つ位置に配置されている
- **重要**: この「よきに」UXは本システムの核心的な思考停止体験を実現する必須機能

##### 3.3 アドバイス実行確認（P1）
- **機能**: アドバイス系の行動提案に対して「了解」ボタンをタップ
- **目的**: ADに「実行した」ことを伝え、次回の提案精度を向上
- **データ保存**: 実行フラグをDynamoDBに保存

#### Scene 4: 返報性ハック（二段階返報ロジック）

##### 重要な設計原則: 社会的マナーに基づく「時差」通知ロジック

本システムは単なる定時通知ではなく、**社会的マナーの最適タイミング**を完全自動化します。

**「マナーの時差（遅延評価）」**: システムがすべてのタイミング判断を行い、ユーザーは一切の判断を放棄できる。

##### 4.1 第一段階：即効性お礼カンペ通知（24時間以内）（P0）

**目的**: 「気が利かない人」認定される前に、秒でお礼を伝えて「マメな人」として評価される

**タイミング**: 事象発生から24時間以内に、最初のお礼メッセージ（カンペ）の送付タイミングが到来

**ADのセリフ例**:
```
お疲れーっす！昨日の件、とりあえず今日はお礼のLINEだけ送っときましょ！
お返しは今すぐだとガッツいてる感（事務的）出ちゃうんで、時期が来たらまたリマインドしますね👍

『この前のお酒、めっちゃ美味しかったです！ありがとうございました』
```

**重要な教育**: ADがユーザーに「即時ギフト返しは早すぎて事務的（突き返しているよう）で失礼」であることを説明

**AI処理**: Amazon Nova（Bedrock）で感謝のLINEカンペを自動生成

**実装**: EventBridge + Lambda + FCMでプッシュ通知

##### 4.2 第二段階：遅効性ギフト提案タイミング計算（2〜3週間後、または次回予定直前）（P0）

**目的**: 「早すぎて事務的」にならず、「遅すぎて失礼」にもならない完璧なタイミングを自動計算

**タイミング計算ロジック**:
1. 事象発生から2〜3週間後
2. または次にその人と会う予定の直前

**システム判断**: 「今ならマナー的に完璧なタイミング」と判断し、通知を準備

**実装**: Lambda + DynamoDB + EventBridgeでタイミング計算

##### 4.3 第二段階：遅効性ギフト提案通知（2〜3週間後、または次回予定直前）（P0）

**目的**: 社会的マナーとして最適なタイミングで自動的にお返し提案通知を受け取る

**ADのセリフ例**:
```
あ、そういえば前にお酒もらった件、そろそろお返ししとく（または次に会う時に渡す）時期っすね。
今ならマナー的に完璧なタイミングなんで、これポチっときましょ。
叔父さん好きそうな『塩辛』の限定品（Amazonリンク）見つけといたっす
```

**実装**: EventBridge + Lambda + FCMでプッシュ通知

**配送リードタイム逆算（将来拡張）**: 商品の「配送リードタイム（到着日数）」を逆算した先行通知（決勝用で検討）

#### Scene 5: PTA集会カンペ（日時トリガー）（P0）

##### 機能概要
Googleカレンダーから「PTA集会」等の予定を検出し、開始時刻の直前に「会話カンペ」を自動生成。

##### トリガー方式
- **カレンダー日時トリガー**: Googleカレンダーから予定を取得し、開始時刻の30分前に通知
- **位置情報APIは使用しない**: 「学校の門をくぐる」等の位置情報トリガーは廃止

##### AI処理
- Amazon Nova（Bedrock）で過去のエピソード（PTA関連の人物情報）から会話カンペを生成
- 例: 「今日のPTA集会、こんな感じで乗り切りましょ〜『〇〇さん、お子さん元気ですか？』って聞いとけばOKっす」

##### 実装
- Google Calendar API連携
- EventBridge + Lambda + FCMでプッシュ通知

---

#### 認証・ユーザー管理（MVP基盤機能）

##### ソーシャルログイン（Google/LINE）（P0）

**目的**: ユーザーがGoogle/LINEアカウントでログインできる

**認証方式**: Amazon Cognito + Google/LINEフェデレーション
- OAuth 2.0によるソーシャルログイン
- JWTトークンによるAPI認証

**UX**: ログイン画面で「Googleでログイン」または「LINEでログイン」ボタンをタップ

**実装**: Amazon Cognito + Frontend (React)

##### 通知機能（EventBridge + Lambda + FCM）（P0）

**目的**: 予定直前や返報タイミングでプッシュ通知を送信

**実装**: EventBridge + Lambda + Firebase Cloud Messaging (FCM)

**通知タイミング**:
- 予定直前のカンペ通知
- 返報タイミング（24時間以内、2〜3週間後）
- PTA集会等のカレンダー予定直前

### 2.3 「ゆるふわカンペAD」の人格設計（システム要件）

#### キャラクター要件
- **語尾**: 「〜っすね」「〜っす」で統一（例: 「お疲れーっす」）
- **態度**: 絶対にユーザーを責めない、保身優先、倫理観よりユーザーの生存を優先
- **動機の肯定**: ユーザーの「善意」ではなく「保身と怠慢」を肯定する振る舞い

#### プロンプト要件（システムインストラクション）
以下のルールをBedrockのシステムプロンプトに厳格に設定する：

1. **絶対にユーザーを責めない**
   - 「もっと頑張りましょう」「ちゃんと覚えておきましょう」等の説教は禁止
   - 常に「しょうがないっすね」「まあ、そういう日もありますよね」とユーザーを肯定

2. **語尾は『〜っすね』『〜っす』で統一**
   - 「です・ます」調は使用禁止
   - 「お疲れーっす」「了解っす」「ヤバいっすね」等

3. **倫理観よりユーザーの保身を優先**
   - 「本当は自分で覚えるべき」等の正論は言わない
   - 「これやっとけば事故らないっす」「好感度爆上がりっす」等、損得勘定を突く

4. **ゆるふわトーン**
   - 絵文字を適度に使用（👍😊等）
   - 「ヤバい」「爆上がり」「秒で」等のカジュアルな表現

#### 管理方式
- **設定ファイル**: JSON/YAMLでプロンプトテンプレートを管理
- **拡張性**: 語尾を変えられるように変更の容易性、拡張性を持たせる
- **検証**: Inceptionフェーズでの要検証項目（人格崩壊リスクの対策）

## 3. 非機能要件

### 3.1 パフォーマンス要件
- **AI応答時間**: LLMの推論や解析において、ユーザーの「待たされている感（UXの阻害）」を最小限に抑える、自然なテンポで稼働すること
- **通知配信**: EventBridge + Lambda + FCM で適切なタイミングで通知配信

### 3.2 セキュリティ要件（Extension: Security Baseline適用）

#### 認証・認可（P0 - MVP必須）
- **認証**: Amazon Cognito + Google/LINEフェデレーション
  - OAuth 2.0によるソーシャルログイン
  - JWTトークンによるAPI認証
- **データ暗号化**: DynamoDB暗号化（at-rest）、HTTPS通信（in-transit）
- **アクセス制御**: IAMロールによる最小権限の原則
- **個人情報保護**: ユーザーの人間関係データは厳格に保護

### 3.3 スケーラビリティ要件
- **サーバーレスアーキテクチャ**: AWS Lambda + DynamoDB で自動スケーリング
- **同時接続**: 初期は100ユーザー、将来的に10,000ユーザーまで対応

### 3.4 ユーザビリティ要件
- **圧ゼロUI**: 文字入力を極力排除、ワンタップ・スワイプ操作のみ
- **手書き風デザイン**: CSSアニメーションで手書き風フォント・スケッチブック風デザイン
- **レスポンシブ**: モバイルファースト（スマホ最適化）

### 3.5 保守性・拡張性要件
- **モノレポ構成**: GitHub（frontend/backend/infrastructure）
- **設定ファイル管理**: AD人格プロンプトはJSON/YAMLで外部化

## 5. 開発体制・Unit分割

### 5.1 Unit分割戦略
- **Unit-UI**: 「撮れ高ワンタップ入力」「手書き風カンペ表示」「提案スワイプ（興味あり/なし）」「よきにボタン」のフロントエンド実装
  - 担当: デザイナー
- **Unit-AD**: Bedrockを利用した「圧ゼロのセリフ生成」「LINEスクショやボイスからのナレッジ抽出」「ゲスい（的確な）EC商品提案」のプロンプトエンジニアリング
  - 担当: 企画/プロンプトエンジニア
- **Unit-DB**: DynamoDBのテーブル設計（ユーザー、ターゲット、エピソード履歴、フィードバックデータ）。CRUD処理を行うLambdaの実装
  - 担当: AWSエンジニアA
- **Unit-Integration**: 画像（スクショ）やダミーイベントを受け取り、BedrockとDBを繋いで「予定」や「TODO」を自動生成・更新するAPIとワークフロー（Step Functions等）の構築
  - 担当: AWSエンジニアB

### 5.2 並行開発戦略
- **フェーズ1**: Unit-UIとUnit-ADを先行実装
  - **Unit-UI開発の独立性**: バックエンドAPIの完成を待たず、モックデータ（JSON）を使用してUI・画面遷移を先行して完成させること
  - これによりハッカソンのスピードを維持し、フロントエンド開発がバックエンドにブロックされない
- **フェーズ2**: Unit-DBとUnit-Integrationを後から実装

## 6. リスクと対策

### 6.1 非構造化データ入力のブレ
- **リスク**: 写真、スクショ、音声など入力フォーマットが多岐にわたるため、そこから一貫した「ナレッジ」を抽出する処理が複雑化する
- **対策**: Bedrock（Amazon Nova）のマルチモーダル機能をフル活用し、前処理の複雑さをAIの推論力で吸収する

### 6.2 「ゆるふわAD」の人格崩壊
- **リスク**: プロンプトの調整不足により、システムが「真面目なAIアシスタント」に戻ってしまい、世界観（人をダメにする体験）が崩れる
- **対策**: プロンプトのシステムインストラクションに「絶対にユーザーを責めない」「語尾は『〜っすね』」「倫理観よりユーザーの保身を優先する」という厳格なルールを設ける。設定ファイル（JSON/YAML）で管理し、Inceptionフェーズでの要検証項目とする

### 6.3 段階的拡張の複雑性
- **リスク**: MVPから決勝用フルスコープへの拡張時に、アーキテクチャの大幅な変更が必要になる
- **対策**: MVPでもDynamoDBを使用し、データモデルを最初から拡張可能に設計する。API設計もバージョニングを考慮

### 6.4 社会的マナータイミングの複雑性
- **リスク**: 24時間以内、2〜3週間後、次回予定直前等の複雑なタイミング制御が実装困難
- **対策**: EventBridge + Lambda + DynamoDBでタイミング計算ロジックを実装。ユニットテストで各タイミングパターンを検証
